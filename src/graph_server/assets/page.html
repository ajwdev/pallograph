Reading the rule graph

What is drawn

Boxes
Each box is a predicate (a relation). Its color says which rule file defines it; click colors in the header to open the legend that maps colors to files (it stays open until you close it). Hover a file in the legend to highlight its predicates, click to keep the highlight.
Cylinders
Data sources (EDB): predicates with facts but no rules, where the data comes from. Shape says derived (box) or source (cylinder); color says where it is defined. Grey cylinders are supplied at runtime: nothing in the rules produces their rows, so they come from outside the program. Usually that is the Kubernetes loader (k8s, object_label, ...), but it can be a datasource in pallograph.toml (cluster_admin_allowed), facts you add with +fact or source (access_request), or a test. A Decl in rules/00_k8s_prelude.mg documents their columns. The graph infers this from the rules alone, without reading the Rust code. Colored cylinders, such as selector_target_kind, are lookup tables written as facts in that rule file.
Arrows
By default arrows follow the data: from what is supplied at runtime at the top, down through each rule that uses them, the order the engine derives facts in. The flip link points them the other way, from a rule's head to what it depends on, like a pprof call graph.
Line thickness and xN labels
How many rules use that dependency. x3 on selector_declared → selector_candidate means three of selector_candidate's rules read selector_declared (three rules, not three predicates). Thicker lines mean more rules, growing with the log of the count and capped, so one busy edge doesn't swamp the picture. Hover the predicate to read the rules.
Red dashed line ending in a bar
Negation: at least one rule uses the predicate with !, so the head holds only when that predicate does not, as in orphaned_sa(N, S) :- serviceaccount(N, S, _), !sa_in_use(N, S). The engine must finish the negated predicate first (a stratum boundary). One negated rule is enough to make the line red; hover to see which rule has the !.
Small loop on a box
Recursion: one of the predicate's rules uses the predicate itself, as transitive closures like controls_identity do.
A line running back up the page
A longer recursive cycle through several predicates. Layout has to point one edge of every cycle upward.

Getting around

Hover a box
Blue lines and boxes: what it depends on. Orange: what uses it. Everything else fades. The rules panel on the right shows its rules.
Click / shift-click
Click keeps the highlight while you read; shift-click highlights the whole chain both ways. Click empty space or press Esc to clear.
Double-click, or focus here in the panel
Re-centers the page on that predicate. A focused page walks a few hops each way; the header's −/+ links change how many, users only shows only what uses it, and whole graph drops the focus.
Rules panel
Each statement with its file:line and the comment above it. Predicate names are links: blue ones are drawn here (click jumps to them), purple ones are not (click shows their rules). added this session marks rules added with define or source. Drag the panel's edge to resize, r hides it.
Keys
? this help, r rules panel, Esc clear or close, Ctrl+F finds a predicate by name.

The URL

Every view is a URL, so it can be bookmarked or shared: focus=PRED, depth=N (hops toward what it depends on), users=N (hops toward what uses it), down (users only), hide=A,B, stop=A,B (drawn but not walked past), files (one box per file), boxes (group by file), topdown (flipped arrows). /graph.dot and /graph.json give the same view as Graphviz dot or JSON.
