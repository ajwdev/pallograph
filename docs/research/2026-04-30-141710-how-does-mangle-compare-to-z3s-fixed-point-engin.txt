● Both are fixed-point Datalog engines, but they differ significantly in design
  goals:

  Z3 Spacer (PDR/IC3)
  - Targets Horn clause verification: finds invariants that prove or refute a
  property
  - Uses SMT reasoning internally — handles arithmetic, bitvectors, arrays
  - Output is a proof/counterexample, not a fact set
  - Scales poorly on large EDBs; the constraint-solving overhead is expensive
  per clause

  Mangle
  - Targets bottom-up evaluation over a concrete fact store
  - Pure Datalog (no arithmetic constraints beyond built-in functions like
  :list:member)
  - Semi-naive fixpoint: only re-derives facts that could have changed each
  round — efficient for large EDBs
  - Stratified negation-as-failure, but no true negation or quantifier
  alternation
  - Output is the full derived IDB — you query it after evaluation

  Key tradeoffs:

  ┌────────────────────────┬──────────────────────┬─────────────────────────┐
  │                        │        Mangle        │      Z3 Fixedpoint      │
  ├────────────────────────┼──────────────────────┼─────────────────────────┤
  │ EDB scale              │ Good (in-memory fact │ Poor (SMT per clause)   │
  │                        │  store)              │                         │
  ├────────────────────────┼──────────────────────┼─────────────────────────┤
  │ Arithmetic/constraints │ No                   │ Yes (full SMT)          │
  ├────────────────────────┼──────────────────────┼─────────────────────────┤
  │ Recursive rules        │ Yes (semi-naive)     │ Yes (PDR for CHC)       │
  ├────────────────────────┼──────────────────────┼─────────────────────────┤
  │ Negation               │ Stratified NAF only  │ Full                    │
  │                        │                      │ under-approximation     │
  ├────────────────────────┼──────────────────────┼─────────────────────────┤
  │ Use case               │ Policy/query over    │ Safety/reachability     │
  │                        │ data                 │ proofs                  │
  └────────────────────────┴──────────────────────┴─────────────────────────┘

  For pallograph's use case — evaluating RBAC, label selectors, and reachability
   over a K8s cluster snapshot — Mangle is the right fit. Z3's fixed-point
  engine would let you express richer properties (e.g., "there exists no path
  from SA X to secret Y under any RBAC binding") but would be far slower and
  require encoding the EDB as Horn clauses rather than loading raw facts.

❯ Got it. Is there a way to pipe facts from Mangle into Z3                      

● There's no existing bridge, but it's buildable. The natural seam is Z3's
  fixedpoint API (its built-in Datalog engine), which accepts ground facts and
  Horn rules in the same format.

  Two practical approaches:

  1. Export Mangle's derived IDB as ground facts → Z3 Horn clauses
  After EvalProgram(), iterate the fact store and emit each derived fact as a
  unit clause in SMT-LIB2:
  (declare-rel can (String String String))
  (rule (can "alice" "get" "pods"))
  (rule (can "bob" "*" "*"))
  Then write your verification query as a Horn clause Z3 has to solve — e.g.,
  "does any principal with can(_, "*", "*") also reach a sensitive namespace?"
  Z3 handles the universal/existential reasoning Mangle can't.

  2. Export Mangle rules + EDB directly as Z3 Datalog
  Skip Mangle's evaluation entirely for certain rule strata and re-express them
  in Z3's fixedpoint dialect. Lets Z3 reason over the rules rather than just the
   derived facts. More powerful but more work to translate Mangle syntax →
  SMT-LIB2 (rule ...) forms.

  Practical friction:
  - Go Z3 bindings (go-z3) are thin and incomplete; you'd likely emit SMT-LIB2
  files and shell out to z3
  - Mangle's built-in functions (:list:member, :match_field) have no Z3 analog —
   those facts need to be pre-expanded before export
  - Ground fact sets from a real cluster can be large; Z3's Datalog engine
  doesn't scale as well as Mangle's semi-naive evaluation

  Best fit for pallograph: use Mangle for the heavy EDB evaluation (RBAC
  flattening, label matching, reachability), then export a filtered subset of
  derived facts to Z3 only for queries requiring arithmetic or universal
  quantification — e.g., proving that no path exists, or reasoning about numeric
   resource limits.

● The realistic options:

  Crepe (v0.2.0, Dec 2025 — actively maintained)
  - Proc-macro Datalog: rules compile directly to Rust code
  - Semi-naive evaluation, stratified negation, auto-generated indices
  - Souffle-competitive on transitive closure at 10⁶ relations
  - Key advantage for pallograph: you call arbitrary Rust functions inline in
  rules, so :list:member and :match_field are just Rust iterators — no upstream
  contribution needed
  - Downside: no aggregation, no temporal facts

  Ascent (547 stars, academic papers, moderate activity)
  - Also proc-macro, similar embedding story to Crepe
  - Adds: aggregation, lattice-based fixed points, parallel eval via Rayon, WASM
   compat
  - "Bring Your Own Data Structures" for relation backing
  - More features but heavier; last commit cadence unclear

  Differential Dataflow (Frank McSherry)
  - Not really Datalog — it's an incremental computation framework (timely
  dataflow)
  - Impressive perf for streaming/incremental updates (µs per update at scale)
  - Complete overkill for batch policy analysis over a static cluster snapshot
  - Would be relevant if you needed live watch-based re-evaluation as K8s
  objects change

  For pallograph specifically: Crepe or Ascent are the right fit. Both let you
  call Rust functions from rules, which sidesteps the missing-predicates problem
   entirely — you'd implement :list:member as a normal Rust iterator call rather
   than a built-in. Ascent wins if you need aggregation (which your current
  rules use). Crepe wins if you want simplicity and a smaller dependency
  footprint.

● Short answer: no, and it would be non-trivial to make it work.

  DDlog wasn't just "Datalog + DD bolted together" — it was purpose-built as a
  DD frontend. The compiler translated Datalog rules into DD operator graphs
  (Collection::join, iterate, etc.), so incremental updates propagated
  automatically through the operator topology.

  Crepe's proc macro generates a fundamentally different execution model: nested
   loops over HashSets with semi-naive delta tracking. There's no operator
  graph, no timely worker threads, no Collection type — the two execution models
   are incompatible at the representation level. You'd essentially need to write
   a new Crepe codegen backend that emits DD operators instead of hash map
  operations. That's roughly what DDlog's compiler did, and it was a significant
   engineering effort.

  Ascent is the same story — batch evaluation, no DD integration, no incremental
   output.

  If you actually need incremental re-evaluation (e.g., live-watch K8s objects
  and re-run policy rules as objects change), your realistic options are:
  1. Use DD directly with raw operator API — no Datalog sugar, you write
  joins/iterates by hand
  2. Re-run the full batch eval on change (probably fine for pallograph's use
  case — cluster snapshots aren't huge)
  3. Wait and see if anyone builds a new DDlog-style frontend on top of DD —
  nothing credible exists right now

  For pallograph's current scope (batch analysis over a snapshot), full
  re-evaluation on change is almost certainly fast enough that DD's incremental
  machinery isn't worth the complexity.

❯ How hard would be to implement something like ddlog if I used Mangle as the   
  frontend?                                                                     

● Meaningfully less work than DDlog was, because the hardest part — the frontend
   — is already done.

  What Mangle already gives you for free:
  - .mg parsing and AST
  - Stratification (ordering rules to handle negation safely)
  - Bound checking
  - Lowering to a physical Op IR with HashJoin, Scan, Filter, Negate, Aggregate
  etc.

  DDlog had to build all of that from scratch. You'd just be writing a new
  codegen backend: a mangle-dd-codegen crate that walks the Op tree and emits DD
   operator calls instead of the current interpreter or WASM output.

  The mapping is fairly direct:

  ┌───────────────────┬──────────────────────┐
  │     Mangle Op     │    DD equivalent     │
  ├───────────────────┼──────────────────────┤
  │ HashJoin          │ Collection::join     │
  ├───────────────────┼──────────────────────┤
  │ Scan / Filter     │ Collection::filter   │
  ├───────────────────┼──────────────────────┤
  │ Negate            │ Collection::antijoin │
  ├───────────────────┼──────────────────────┤
  │ Aggregate         │ Collection::reduce   │
  ├───────────────────┼──────────────────────┤
  │ Map / Project     │ Collection::map      │
  ├───────────────────┼──────────────────────┤
  │ Recursive stratum │ iterate { ... }      │
  └───────────────────┴──────────────────────┘

  EDB predicates become DD InputCollections; updates to those collections
  propagate incrementally through the operator graph.

  The hard parts:
  - Stratified negation across strata — DD's iterate handles intra-stratum
  recursion fine, but negation requires the negative relation to be fully
  materialized from a prior stratum before the current one starts. Getting the
  inter-stratum wiring right is where DDlog's compiler did most of its heavy
  lifting.
  - Mangle Value in DD — DD requires Ord + Hash + Clone on all collection
  elements. Mangle's Value enum probably satisfies this already but you'd need
  to verify.
  - Missing predicates — :list:member and :match_field still need implementing,
  but in this architecture they'd be DD flat_map operations, which is natural.
  - IR stability — mangle-rs is a one-author project; the Op IR isn't a
  guaranteed stable API.

  Rough effort: 3-5 weeks for someone comfortable with both the Mangle IR and
  DD's API. The stratification wiring is the only part with real gotchas.

  Worth it for pallograph? Probably not yet — full re-evaluation on a cluster
  snapshot is going to be fast enough that DD's incremental machinery isn't
  buying you anything. It would matter if you were watching a live cluster and
  needed sub-millisecond policy re-evaluation on every object change.

❯ Can you explain this more and dumb it down a bit for me: "Stratified negation 
   across strata"                                                               

● Sure. Start with a concrete example. Say you have two rules:

  % Rule 1: Alice is "dangerous" if she can delete pods
  dangerous(alice) :- can(alice, "delete", "pods").

  % Rule 2: Bob is "safe" if he is NOT dangerous  
  safe(bob) :- NOT dangerous(bob).

  For rule 2 to give a correct answer, you must finish computing all of
  dangerous first. If you try to evaluate safe and dangerous at the same time —
  interleaved — you might check "is bob dangerous?" before you've finished
  deriving all the ways someone could be dangerous. You'd get a wrong answer.

  Stratification is the compiler's solution: sort the rules into layers
  ("strata") so that anything involving negation only looks backwards at
  already-completed layers.

  Stratum 1: compute dangerous(...) — run to fixpoint
  Stratum 2: compute safe(...)     — now NOT dangerous is safe to evaluate

  Why this is the hard part with DD:

  DD's iterate { } block is great for recursion within a stratum — it keeps
  looping until no new facts appear. But iterate doesn't know about the boundary
   between strata. You have to manually wire it up so stratum 2's operator graph
   only starts consuming dangerous after stratum 1's iterate has fully converged
   and closed.

  In DDlog, the compiler handled this wiring automatically. If you're building
  it yourself, you have to read the stratification order out of Mangle's
  analysis output and sequence your DD scopes accordingly. It's not conceptually
   hard once you understand why it matters — but it's easy to get subtly wrong.

❯ What did the compiler do specifically? I imagine Mangle also has to handle    
  this                                                                          

● Both have to solve the same problem. The difference is where the solution
  lives.

  In Mangle's interpreter it's simple because execution is imperative:

  for each stratum in order:
      loop:
          run all rules in this stratum
          if no new facts derived: break
      # stratum is now "frozen" — move on

  The facts from stratum 1 just sit in the fact store. When stratum 2 evaluates
  NOT dangerous(X), it queries the store, which is already complete. Sequential
  execution makes the ordering automatic.

  In DDlog's compiler it was harder because DD is a dataflow graph — you're not
  executing steps, you're wiring up operators that run continuously. The
  compiler had to generate something like:

  // Build stratum 1's operator graph, run it to convergence
  let dangerous = scope.iterate(|inner| {
      // recursive rules for `dangerous`
  });
  // Advance the frontier — DD's signal that this collection is "done"
  // dangerous is now sealed

  // Build stratum 2's graph, with dangerous as a static input
  let safe = something.antijoin(&dangerous); // NOT dangerous

  The critical piece is advancing the frontier. DD uses timestamps to track
  which updates are still pending. When you advance a collection's frontier past
   the computation time, you're telling downstream operators "this collection
  will never change again — you can safely use it in negation." DDlog's compiler
   automated that frontier management between strata.

  If you built a Mangle → DD backend, this is exactly what you'd need to
  generate: read Mangle's stratification order from the analysis output, and for
   each stratum boundary, emit the frontier advancement code before wiring up
  the next stratum's operators.

● Roughly, something like this for a two-stratum program:

  timely::execute(|worker| {
      // -- EDB inputs (your raw facts) --
      let (mut sa_handle, service_accounts) = worker.new_collection::<Value>();
      let (mut rb_handle, role_bindings)    = worker.new_collection::<Value>();
      let (mut rp_handle, role_perms)       = worker.new_collection::<Value>();

      // -- Stratum 1: derive `dangerous` (possibly recursive) --
      let dangerous = role_bindings
          .join(&role_perms)          // SA -> Role -> (Verb, Resource)
          .filter(|(_, verb, res)| verb == "*" && res == "*")
          .map(|(sa, _, _)| sa)
          .iterate(|inner| {          // if rules were recursive
              // ... recursive cases
              inner
          });

      // -- Stratum 2: `safe_sa` uses NOT dangerous --
      // antijoin = "things in left that have no match in right"
      let safe_sa = service_accounts.antijoin(&dangerous);

      // -- Load your facts --
      sa_handle.insert(Value::Name("alice".into()));
      rb_handle.insert(/* ... */);

      // -- Advance frontier: signal "no more facts at timestamp 0" --
      sa_handle.advance_to(1); sa_handle.flush();
      rb_handle.advance_to(1); rb_handle.flush();
      rp_handle.advance_to(1); rp_handle.flush();

      // -- Drain the dataflow until fully converged --
      while probe.less_than(&1) {
          worker.step();
      }

      // query results from safe_sa...
  });

  The key things to notice:

  - iterate { } handles recursion — DD keeps looping internally until no new
  facts appear, then the output "leaves" the loop fully converged
  - antijoin handles NOT — it's "everything in the left collection that has no
  matching key in the right collection"
  - advance_to(1) + flush() is the frontier advancement — you're telling DD "I'm
   done inserting facts at time 0, nothing more is coming". Downstream operators
   won't fire until they know the frontier has passed
  - worker.step() just drains pending work; the while probe.less_than loop runs
  until everything has converged

  The part the DDlog compiler automated was generating all of this from Datalog
  rules. The join/antijoin/iterate wiring, the frontier advancement, the
  worker.step() loop — all of it was emitted by the compiler based on the
  stratification order. Doing it by hand for one rule set is tractable; doing it
   for arbitrary .mg files is what the backend would generate.

● Yes, Mangle has an IR. The mangle-ir crate has an Op enum with exactly what
  you'd expect: Seq, Iterate (scan over a relation), Filter, Insert, Let
  (variable binding), GroupBy, HashJoin. Plus a DataSource type with Scan,

  On "interpreter mode" for DD — this is actually the key insight, and it's good
   news.

  DD dataflow graphs are constructed at runtime in normal Rust code inside a
  closure. There's no macro magic, no compile-time graph. So you wouldn't write
  a codegen that emits Rust source. You'd write a runtime interpreter that walks
   Mangle's Op tree and calls DD operator methods as it goes, building up the
  graph dynamically:

  fn op_to_dd(op: &Op, collections: &mut HashMap<String, Collection<Value>>) {
      match op {
          Op::HashJoin { build, probe, .. } => {
              let left  = collections[build];
              let right = collections[probe];
              let joined = left.join(&right);
              // store joined back into collections
          }

  2. Walk the Op tree + stratification order, call DD operators to wire up the

  4. worker.step() loop until convergence

      // ... wire up new operators from updated Op IR
  });

  - EDB collections → arranged on startup, trace handles kept alive permanently
  - Incremental K8s updates → +1/-1 mutations, advance frontier

  Declaring relations:

  DDlog required explicit typed declarations:
  input relation RoleBinding(sa: string, role: string, namespace: string)
  output relation HasPerm(sa: string, verb: string, resource: string)

  Mangle has no declarations — relations emerge from rules and facts:
  % facts just exist
  role_binding("alice", "edit", "default").

  Rules look similar but Mangle is more Prolog-like:

  DDlog:
  HasPerm(sa, verb, resource) :-
      RoleBinding(sa, role, _),
      RolePermission(role, verb, resource).

  Mangle:
  has_perm(SA, Verb, Resource) :-
      role_binding(SA, Role, _),
      role_perm(Role, Verb, Resource).

  Superficially similar. Main visual differences: DDlog capitalized relation
  names, Mangle capitalizes variables (Prolog convention). DDlog used lowercase
  variable names.

  Where DDlog diverged significantly — algebraic data types:

  DDlog had full ADTs, which standard Datalog doesn't:
  typedef Permission = Permission { verb: string, resource: string }
  typedef Subject = User { name: string }
                 | Group { name: string }
                 | ServiceAccount { name: string, namespace: string }

  input relation Binding(subject: Subject, role: string)

  Mangle has no ADTs — you use structured values (/name constants, lists, maps)
  but no declared type variants.

  Extern functions — DDlog's Rust escape hatch:

  extern function match_label(selector: Map<string,string>, labels:
  Map<string,string>): bool

  HasMatch(obj) :- Object(obj, labels), Selector(sel), match_label(sel, labels).

  This was explicitly DD-specific: extern functions compiled to Rust function
  calls in the generated output. Mangle has no equivalent — built-ins only, no
  arbitrary Rust/Go callouts.

  The input/output distinction was DD-specific:

  In DDlog input relation mapped directly to a DD InputSession — something you
  could push +1/-1 updates into at runtime. output relation was a derived DD
  Collection. This distinction had no semantic meaning in Datalog terms — it was
   purely an artifact of the compilation target.

  Mangle has no such distinction. All predicates are just predicates.

  Multiset semantics — the weird one:

  Because DD operates on weighted collections (the +1/-1 model), DDlog inherited
   bag semantics rather than set semantics. A fact could technically have
  multiplicity > 1. Standard Datalog is set-based. This caused subtle bugs if
  you weren't careful — inserting the same fact twice could give you a count of
  2 rather than 1, and you had to be explicit about deduplication. Mangle is
  set-based throughout.

  Summary:

  DDlog was closer to a typed functional language with Datalog-style rule syntax
   than to standard Datalog. The type system, ADTs, extern functions, and
  input/output modifiers were all non-standard extensions. Mangle is much closer
   to standard Datalog — more Prolog-flavored, dynamically typed, no DD-specific
   concepts baked into the syntax.

  If you're building the Mangle→DD backend, this is actually an advantage:
  Mangle's syntax doesn't expose the DD model at all, so users write standard
  Datalog and the backend handles the InputSession/Collection mapping
  transparently.

● This is the most fundamental mismatch and it touches every layer of the port.

  DD's weight model:

  Every fact in DD has an integer weight. +1 means exists, 0 means gone, -1
  means retracted. But nothing stops a fact from having weight 2, 3, etc. —
  that's valid in DD's algebra even if it's semantically weird. When you join
  two collections, the result weight is the product of the input weights:

  role_binding("alice", "edit")  weight=2  ← inserted twice
  role_perm("edit", "get", "pods")  weight=1

  join result: ("alice", "get", "pods")  weight=2   ← wrong

  Mangle's semantics say that fact just exists once. DD disagrees.

  Where duplicates actually come from in your use case:

  1. Watch reconnects — K8s watchers relist on reconnect, resending InitApply
  events for all existing objects. If you naively +1 on every InitApply without
  tracking what you've already inserted, you get weight 2 on every object in the
   cluster.
  2. Multiple rule paths deriving the same fact — your rbac.mg has exactly this.
   Three separate paths all produce has_perm(SA, Verb, Resource):
    - SA → RoleBinding → Role
    - SA → RoleBinding → ClusterRole
    - SA → ClusterRoleBinding → ClusterRole

  If all three fire for the same tuple, DD gives it weight 3. Mangle gives it
  weight 1.
  3. Recursive rules — in the iterate {} block, semi-naive evaluation tracks
  deltas. Duplicates in base facts produce wrong deltas.

  The join weight multiplication is the real danger:

  It propagates silently. Weight 2 facts going into a join produce weight 2
  outputs, which go into the next join producing weight 4, and so on. By the
  time you're doing aggregation (count, collect) downstream, your numbers are
  completely wrong and there's no error — just silent bad results.

  The fix: distinct()

  DD has a distinct() operator that collapses any positive weight to 1 and drops
   negatives. DDlog's compiler inserted these automatically because it had
  explicit output relation declarations — it knew the materialization
  boundaries.

  You have no such markers in Mangle. Your options:

  Option A — Sanitize at the EDB boundary (minimum viable):
  let k8s = k8s_input_collection.distinct();
  // all downstream derivations see clean weight-1 facts
  This works if your rules don't have multiple paths deriving the same IDB fact.
   For pallograph they do, so this alone isn't enough.

  Option B — distinct() after each stratum:
  // after stratum 1 converges
  let has_perm = iterate(|inner| { ... }).distinct();

  // stratum 2 sees clean input
  let dangerous = has_perm.filter(...).distinct();
  Safe but adds overhead at every stratum boundary.

  Option C — Track insertions at the application layer:
  Before calling k8s_input.update(fact, +1), check if it's already in with
  weight 1. If so, skip. This handles the watch reconnect case but not the
  multiple-derivation-path case.

  Practical strategy for pallograph:

  You need both A and B. Apply distinct() to all EDB collections on creation,
  and apply distinct() to the output of any relation that can be derived by
  multiple rule paths — which you can determine statically from the Op IR (look
  for Op::Seq where multiple branches Insert into the same relation).

  The good news: Mangle's analysis already knows the rule structure. When
  building the DD operator graph from the IR, you can identify union points
  automatically and insert distinct() there. It's mechanical, just needs to be
  explicit. DDlog did this automatically; your Op walker would need to do the
  same.

● Mangle + Differential Dataflow: Design Memo

  Background

  Pallograph currently uses the Go Mangle library for Datalog-based K8s policy
  analysis — batch evaluation over a cluster snapshot. The question explored:
  can we get DDlog-style incremental re-evaluation (only recompute what changed)
   while keeping Mangle's .mg syntax?

  ---
  Why Not DDlog

  DDlog is the obvious precedent but hasn't been updated in ~4 years. It was
  purpose-built as a Differential Dataflow frontend — useful as a reference but
  not a dependency to take on.

  ---
  The Proposed Stack

  .mg files (Mangle syntax)
      ↓
  mangle-rs frontend (parse → analyze → stratify → Op IR)
      ↓
  Runtime Op walker (builds DD operator graph at startup)
      ↓
  Differential Dataflow (incremental evaluation)
      ↑
  kube-rs watch stream (K8s facts as +1/-1 updates)

  ---
  mangle-rs

  - Lives at codeberg.org/TauCeti/mangle-rs (moved out of google/mangle tree,
  same author — Burak Emir)
  - v0.7.0, April 2026, actively maintained with quarterly releases
  - 14-crate workspace; dual execution: pure Rust interpreter (edge) + WASM via
  wasmtime (server)
  - Has a proper physical IR in mangle-ir: Op enum with Seq, Iterate, Filter,
  HashJoin, GroupBy, Insert, Let and DataSource variants (Scan, ScanDelta,
  IndexLookup)
  - Critical gap for pallograph: :list:member and :match_field are not
  implemented — your rbac.mg rules use both heavily for RBAC flattening. These
  would need to be contributed or worked around as DD flat_map calls.

  The Go Mangle implementation has no IR — it evaluates directly on the AST via
  unification. The Rust port's Op IR is what makes this architecture feasible.

  ---
  How the DD Backend Works

  Unlike DDlog (which was a compiler emitting Rust source), this would be a
  runtime Op walker — no codegen, no rustc invocation:

  fn op_to_dd(op: &Op, collections: &mut HashMap<String, Collection<Value>>) {
      match op {
          Op::HashJoin { .. }              => collection.join(&other),
          Op::Filter { Condition::Negation } => collection.antijoin(&other),
          Op::GroupBy { .. }               => collection.reduce(...),
          Op::Seq(ops)                     => ops.iter().for_each(...),
          // etc.
      }
  }

  Called once at startup when loading .mg files. Graph is fixed after
  construction. All collections use Collection<_, Vec<Value>, isize> — uniform
  value type, loses some type safety but works fine.

  Incremental updates are just DD input mutations:
  // K8s object added
  k8s_input.update(obj_to_tuple(&obj), +1);
  // K8s object removed  
  k8s_input.update(obj_to_tuple(&obj), -1);

  k8s_input.advance_to(next_timestamp);
  k8s_input.flush();
  worker.step_while(|| probe.less_than(k8s_input.time()));

  Only the parts of the computation downstream of the changed fact recompute.
  Everything else is untouched.

  ---
  Stratified Negation — The Hard Part

  Mangle's analysis already handles stratification — it sorts rules into layers
  so negation only looks at fully-computed prior strata. The interpreter handles
   this trivially via sequential execution. DD is harder because you're building
   a dataflow graph, not executing imperatively.

  DD's iterate {} handles recursion within a stratum. For negation across
  strata, you need the negative relation to be fully materialized before the
  downstream stratum's antijoin fires. DD handles this via frontier advancement:
   when a stratum's iterate block converges and its output "leaves" the loop,
  the inner timestamp is projected away and downstream operators see a sealed
  collection.

  Concretely: correctly sequencing the strata means reading Mangle's
  stratification order out of the analysis output and ensuring each iterate
  block's output is fully converged before wiring up the next stratum's
  operators. This is mechanical but the place where subtle bugs live.

  ---
  Multiset Semantics — The Silent Footgun

  This is the most important thing to get right.

  DD operates on weighted collections (+1/-1). Nothing prevents a fact from
  having weight 2+. Join result weights are the product of input weights —
  duplicates propagate and amplify silently through the computation. Mangle is
  pure set semantics (facts exist or they don't).

  Sources of duplicates in pallograph specifically:
  1. Watch reconnects — kube-rs relisters on reconnect, resending InitApply for
  all existing objects. Naively applying +1 on every InitApply gives every fact
  weight 2.
  2. Multiple rule paths — rbac.mg has three separate paths deriving
  has_perm(SA, Verb, Resource). If all three fire for the same tuple, DD weight
  = 3.
  3. Recursive rules — duplicates in base facts corrupt semi-naive delta
  computation.

  The fix: DD's distinct() operator collapses any positive weight to 1. DDlog's
  compiler inserted these automatically at output relation boundaries. You have
  no explicit output declarations in Mangle, so you need to insert distinct()
  at:
  - All EDB input collections on creation
  - Output of any relation derived by multiple rule paths (identifiable
  statically from the Op IR — look for Op::Seq where multiple branches Insert
  into the same relation)
  - Output of each recursive stratum

  ---
  Dynamic Graph Reconstruction (Rule Changes at Runtime)

  If .mg rules change at runtime, you can rebuild the DD operator graph without
  replaying EDB facts using arrangements:

  // EDB arranged once, TraceHandle kept alive permanently
  let k8s_arranged = k8s_collection.arrange_by_key();
  let trace_handle = k8s_arranged.trace.clone();

  // When rules change — new dataflow, same data, no replay
  worker.dataflow(|scope| {
      let k8s = trace_handle.import(scope); // shared reference, no copy
      // rebuild operator graph from new Op IR
  });

  The trace is a persistent, incrementally-maintained index. New dataflow scopes
   start from the current frontier.

  DDlog's syntax was heavily influenced by Rust — strong typing, ADTs, pattern
  matching, extern function for Rust callouts. These were all driven by DD's
  requirements. Mangle is much closer to standard Prolog-style Datalog; users
  write normal rules and the DD substrate is invisible.

  ---
  K8s Integration

  kube-rs (v3.1.0, CNCF Sandbox) has a solid dynamic client story:
  - DynamicObject + GroupVersionKind + API discovery handles arbitrary resource
  types without codegen
  - watcher() gives Applied/Deleted/InitApply/InitDone events — maps directly to
   +1/-1 DD updates
  - InitDone is the signal to advance the frontier and trigger first evaluation
  - CBOR (KEP-4222): open tracking issue, not yet implemented. Alpha in 1.32,
  beta in 1.33. Not blocking.
  - WatchList: implemented.

  If kube-rs ever meaningfully lags on API machinery, the escape hatch is a thin
   Go sidecar only for the watch layer, piping JSON facts to the Rust engine —
  clean architectural seam, doesn't require abandoning Rust for the computation
  layer.

  ---
  Key Risks / Open Questions

  1. :list:member and :match_field — must be implemented before pallograph's
  existing rules work. These are the first thing to tackle.
  2. mangle-ir API stability — one-author project, Op IR not a guaranteed stable
   API. Pin a version.
  3. distinct() placement — getting this wrong produces silent wrong answers,
  not errors. Needs tests with known-duplicate inputs.
  4. Stratification wiring — the place most likely to produce subtle correctness
   bugs. Needs explicit tests for rules with negation across strata.
  5. Vec<Value> join performance — DD's efficiency relies on good hash/ord
  implementations. Vec<Value> comparison is linear in tuple length. Worth
  benchmarking early.
